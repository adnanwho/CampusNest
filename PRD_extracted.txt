CampusNest
Product Requirements Document — Functional Hackathon MVP
AI-Powered Student Accommodation Marketplace with Verified Listings, Live Availability & Blockchain-Backed Verification
1. Document Purpose
This PRD defines the functional CampusNest MVP to be built and deployed for the hackathon. CampusNest is a two-sided accommodation platform: students search for accommodation while property owners/managers list and manage properties. The MVP combines personalized AI recommendations, verified listings, current vacancy information, property comparison, and a blockchain-backed record of CampusNest verification events.
2. Product Vision
CampusNest helps a student moving to an unfamiliar city find accommodation that fits their needs, understand the real cost and commute, see current availability, and understand what CampusNest has verified about a listing. At the same time, property listers receive a structured way to publish properties, complete the CampusNest verification workflow, and maintain current occupancy.
Tagline: Find. Compare. Verify. Decide.
3. Problem Statement
Students relocating from another state or city for college often depend on scattered information from brokers, social groups, referrals, maps, and property platforms. They may struggle to compare rent versus actual monthly cost, commute, facilities, reviews, trust signals, and current vacancy. Property owners also lack a student-focused platform where verified listings and current availability can be presented in a structured way.
4. Target Users
Student / Accommodation Seeker: a student or other user searching for a PG, hostel, flat, or shared accommodation.
Lister: PG owner, hostel operator, flat owner, or property manager who wants to publish and manage a listing.
CampusNest Admin / Verifier: a trusted role that reviews listing verification requests and approves or rejects them.
5. Core Product Model
CampusNest has three product pillars:
AI — helps answer: “Which available property fits me best?”
Marketplace — answers: “Which verified properties are currently available, and what do they cost?”
Trust + Blockchain — answers: “What did CampusNest verify, and can the verification record be independently checked?”
Blockchain is not presented as proof that a physical property is inherently genuine or safe. It provides a tamper-evident record of a CampusNest verification event.
6. High-Level User Journeys
6.1 Student Journey
Open CampusNest.
Choose Student / Accommodation Seeker.
Register or log in.
Complete student profile and accommodation preferences.
Search or request recommendations.
System considers currently available listings and calculates match scores.
Student sees ranked recommendations with AI-generated explanations.
Student opens a property detail page.
Student sees rent, effective monthly cost, commute, facilities, reviews, verification, and current vacancy.
Student compares 2–3 properties.
Student opens the verification record and blockchain transaction.
Student shortlists/decides on an accommodation.
6.2 Lister Journey
Open CampusNest.
Choose Lister / Property Owner.
Register or log in.
Create a property listing.
Enter property, pricing, facilities, location, capacity, and availability information.
Submit the listing for CampusNest verification.
Admin reviews the verification request.
If approved, the listing becomes verified and eligible for student discovery.
CampusNest creates/registers the verification record and associates the blockchain transaction.
Lister manages the listing and updates occupancy/availability.
Students see the latest availability.
6.3 Admin / Verification Journey
Admin opens pending verification requests.
Reviews submitted lister/property information.
Approves or rejects the listing.
On approval, creates a CampusNest verification record.
Associates the verification hash and blockchain transaction.
Verified listing becomes eligible for student discovery.

Available count is calculated from total capacity minus occupied count.
Student-facing availability reflects the latest stored value.
Use simple status labels such as Available, Filling Fast, Almost Full, and Full.
10. Verification System
10.1 What CampusNest Verifies
Lister information according to the hackathon verification workflow.
Property information submitted by the lister.
Address/location information.
Capacity/listing information.
No additional evidence types beyond the four listed above are in scope for the MVP. Any further evidence category (e.g. ownership documents, ID proof) is P1.
The hackathon prototype must clearly communicate that this is a CampusNest verification workflow, not a universal guarantee of safety, legality, ownership, or physical authenticity.
10.2 Verification Flow
Lister → Submit Listing → Under Review → Admin Review → Approved/Rejected → Verified → Blockchain Record → Student Visibility
10.3 Verification Badge
Example:

Property information checked.

Verification date.
Link to verification record.

12.2 AI Responsibility
Explain why a ranked property matches the student.
Use only supplied property/student facts.
Keep explanations concise and specific.
Do not independently invent the numerical score.

13. Live Availability Model
For MVP, 'live tracking' means live/current occupancy and vacancy status, not GPS tracking. The lister updates occupancy; the application stores the latest state; the student side displays the latest availability.
Example:
Lister: 18 occupied / 20 capacity → Student: 2 beds available
Lister updates: 19 occupied / 20 capacity → Student: 1 bed available

verification_records: id, property_id, lister_id, verification_status, record_hash, timestamp, blockchain_tx, reviewed_by.
recommendations: can be computed on demand; storage is optional.

16. Deployment & Technical Principles
The MVP must be deployable and accessible through a public URL.
Backend/business-logic layer: Java/Spring Boot. This is a decision, not an option.
Frontend: Next.js + TypeScript + Tailwind CSS + shadcn/ui, deployed to a public URL accessible in any browser — no native app or browser extension required.
PostgreSQL/Supabase can provide persistent storage.
AI API keys and blockchain private keys must remain server-side and be stored as environment variables.
Frontend users must not be able to directly modify verification fields.
Sensitive personal information must not be stored on-chain.
The application should have graceful loading, empty, and error states.
17. Security & Trust Requirements
Role-based access: students cannot access lister/admin operations.
Listers can only modify their own listings.
Verification status cannot be changed directly by a normal lister.
Admin verification actions must be protected.
No secret/API/private-key values in frontend code.
Validate listing, occupancy, budget, and profile inputs.
Do not expose unnecessary personal information in public property pages.

22. Product Positioning
CampusNest is not positioned as another generic property listing website. Existing platforms already provide discovery. CampusNest focuses on the decision and trust layer for students: matching students to currently available listings, showing the effective cost and commute, exposing the verification status, and making the verification record independently checkable.
23. Honest Product Limitations
The hackathon uses seeded/demo property and review data.
Verification is based on the defined CampusNest prototype workflow and is not a guarantee of physical safety or legal ownership.
Blockchain records the verification event; it does not independently inspect the property.
Availability is only as current as the lister's latest update.
The MVP is a functional hackathon product, not a production marketplace.
24. One-Line Product Definition
CampusNest is a two-sided accommodation platform where verified listers manage current property availability, while students discover and compare available stays through explainable AI recommendations and independently checkable verification records.
